AI Recruitment 部署操作指南

01 / 新环境首次部署 ↗准备基础设施、填写配置，再构建启动。 02 / 已有环境更新发布 ↗保留现有配置，备份、迁移并验证新版本。
先检查部署准备查看验收与回滚配套文件说明

本指南用于自托管环境交付：业务主机运行 Web、Worker、Agent 与业务基础设施，音视频主机运行 LiveKit、Egress 和独立 Redis。应用使用 Web 集成 Hono API 模式。

已有系统发版，走“现有环境更新”；部署一套空环境，走“首次部署”。 两条流程共用部署准备和验收标准。参数含义查阅参数手册，现场差异查阅服务器核对记录。

  • 文档版本：1.6 · 2026-10-15。
  • 核对基线：源码 2056e99a，服务器配置核对时间为 2026-10-15。每次发布在检查单中填写实际目标 SHA；本页不自动指定发布最新代码。
  • 配套文件：应用环境模板、应用 Compose 覆盖模板、发布检查单。均不含真实凭据。

环境准备通过标准

  • 两台 Linux 主机具备 Docker 与 Compose 2.24.0+，部署账号能操作 Docker、部署目录和证书。
  • 新环境域名与证书已准备；应用 / S3 / LiveKit 的 HTTPS/WSS 可达。
  • 音视频主机开放实际配置的 RTC 7881/TCP、50000–60000/UDP，以及 TURN 3478/UDP、5349/TCP；范围与实际配置一致。Worker、Agent、Egress 可以访问媒体网络。
  • 运维完成数据库、私有桶和访问账号初始化；模型账号具有 LLM、OCR、Embedding、Rerank 权限，另有 ElevenLabs 和 MiniMax 凭据。
  • 已选登录方式的回调登记完成。当前代码仍校验 Google 和两套飞书凭据，不能用空值或构建占位值应付运行校验。
  • 新环境基础设施包已确认只挂载新数据目录；已有环境已明确备份、停机窗口与回滚兼容性。

首次部署

适用于全新环境。执行前先完成“部署准备”，将配套文件解压到业务主机 /opt/arc-delivery/，其中包含 templates/。以下每步检查通过再进入下一步。

1 启动业务基础设施

位置：新业务主机 · /opt/arc-infra。 运维先放置完整配置包，填写该包自己的凭据，按包内说明初始化数据库、桶与账号。同步安装文件存储的 Nginx 站点和证书，使 .env 将使用的 S3 Endpoint 在启动应用前已经可达。

bash
cd /opt/arc-infra || exit 1
docker compose -f docker-compose.yml config --quiet &&
docker compose -f docker-compose.yml up -d &&
docker compose -f docker-compose.yml ps
docker network inspect arc-infra_default --format '{{.Name}}'
sudo nginx -t && sudo systemctl reload nginx

通过： PostgreSQL、Redis、Qdrant、MinIO 正常运行，arc-infra_default 网络存在，数据库与私有桶已建好。若基础设施包使用其他网络名，将应用覆盖文件的外部网络名同步为实际名称。配置报错、服务退出或资源未初始化时先修复本步骤。

2 启动音视频基础设施

位置：新音视频主机 · /opt/livekit。 放置完整音视频配置包，安装 LiveKit 的 Nginx 站点，配置域名、证书、Server/Egress 共用的 LiveKit 凭据及 Redis。当前核对版本为 LiveKit v1.13.5、Egress v1.13.0，正式发布以交付包的验收版本为准。

在完整 livekit.yaml 中核对以下字段；将占位符替换为目标应用域名和配置中已有的 LiveKit Key。应用未启动时回调暂不可达，最终必须在验收阶段验证事件投递。

yaml
webhook:
  api_key: "<与应用相同的 LIVEKIT_API_KEY>"
  urls:
    - "https://<目标应用域名>/api/livekit/webhook"
bash
cd /opt/livekit || exit 1
docker compose -f docker-compose.yml config --quiet &&
docker compose -f docker-compose.yml up -d &&
docker compose -f docker-compose.yml ps
curl --fail --silent --show-error http://127.0.0.1:8082/
sudo nginx -t && sudo systemctl reload nginx

通过： LiveKit、Egress、专用 Redis 持续运行，Egress 健康接口成功，LiveKit WSS/TURN 证书与端口匹配配置。8082 为已核对编排的 Egress 健康端口；包内修改了端口时同步调整。真实媒体连通性在后续面试验收中确认。

3 准备应用源码和配置

位置：新业务主机 · /opt。 将目标发布 SHA 从检查单填入。只在应用目录尚不存在时执行克隆。

bash
RELEASE_SHA=__FILL_RELEASE_SHA__
test "$RELEASE_SHA" != __FILL_RELEASE_SHA__ &&
test ! -e /opt/ai-recruitment &&
git clone https://github.com/agniwen/ai-recruitment.git /opt/ai-recruitment &&
git -C /opt/ai-recruitment checkout --detach "$RELEASE_SHA"

位置：新业务主机 · /opt/ai-recruitment。 只在两个目标文件都不存在时安装模板：

bash
cd /opt/ai-recruitment || exit 1
test ! -e .env && test ! -e docker-compose.override.yml &&
install -m 600 /opt/arc-delivery/templates/production.env.example .env &&
install -m 644 /opt/arc-delivery/templates/docker-compose.override.yml.example docker-compose.override.yml

填写 .env 的所有 __FILL_...__；字段按数据库、登录、模型、文件、录像、LiveKit、向量和 Worker 分组。新环境使用独立资源；DATABASE_URL、REDIS_URL 中的地址必须从容器可达。容器里的 localhost 指向容器自身。

这条部署路径只使用根 .env，由三个应用容器共同读取。 不再创建单独的 Agent .env.secrets；不要把生产 .env 复制到 Web/Backend 源码子目录，避免进入镜像构建上下文。

检查占位符时只输出字段名，不输出密钥：

bash
cd /opt/ai-recruitment || exit 1
awk -F= '/^[A-Z][A-Z0-9_]*=/ && /__FILL_/ {print $1; missing=1} END {exit missing}' .env &&
docker compose -f docker-compose.yml -f docker-compose.override.yml config --quiet &&
docker compose -f docker-compose.yml -f docker-compose.override.yml config --services

通过： 没有待填写字段输出，Compose 解析成功，服务列表包含 web、worker、agent。检查单记录域名、功能开关、外部网络及 Secret 版本。这里只检查配置结构，实际凭据权限在验收中确认。

4 构建、迁移并启动应用

位置：新业务主机 · /opt/ai-recruitment。 本流程使用与现有环境一致的源码构建方式。代码版本固定为上一步检出的 SHA，按顺序执行：

bash
cd /opt/ai-recruitment || exit 1
docker compose -f docker-compose.yml -f docker-compose.override.yml build --pull web worker agent &&
docker compose -f docker-compose.yml -f docker-compose.override.yml run --rm --no-deps web node .output/migrate.mjs &&
docker compose -f docker-compose.yml -f docker-compose.override.yml up -d --no-build --wait --wait-timeout 300 web worker agent &&
docker compose -f docker-compose.yml -f docker-compose.override.yml ps

通过： 构建与迁移退出码均为 0，三个应用运行且健康检查通过。Web 正常入口会再次检查迁移记录，不会重复已完成的迁移。构建失败不启动，迁移失败不进入启动步骤；保留错误并按参数手册第八章排查。

若交付采用镜像仓库拉取，交付方需提供三个服务的完整 image: 仓库@sha256:摘要 声明及其验证记录；按该声明发布。仓库基础 Compose 只有 build，不能把本步骤直接改成 pull。

现有环境更新

适用于当前已运行的两台服务器。保留现有三套编排、数据目录与根 .env。 本流程更新应用；基础设施或 LiveKit 有变更时，另外安排对应主机的变更窗口，并记录验收结果。

1 保存旧版本和回滚材料

位置：业务主机 172.237.14.213 · /opt/ai-recruitment。 在修改代码、配置和构建之前执行。下面脚本在 /opt/arc-releases/ 生成时间戳目录，记录输出的目录名，后续步骤使用同一目录。

bash
bash <<'BASH'
set -eu
cd /opt/ai-recruitment || exit 1
umask 077
release_dir="/opt/arc-releases/$(date +%Y%m%d-%H%M%S)"
mkdir -p /opt/arc-releases
mkdir -m 700 "$release_dir"
cp .env docker-compose.yml docker-compose.override.yml "$release_dir/"
git rev-parse HEAD > "$release_dir/previous-source-sha.txt"
printf 'services:\n' > "$release_dir/rollback.images.yml"
for service in web worker agent; do
  container_id=$(docker compose -f docker-compose.yml -f docker-compose.override.yml ps -q "$service")
  test -n "$container_id"
  image_id=$(docker inspect --format '{{.Image}}' "$container_id")
  rollback_tag="arc-rollback-$service:$(basename "$release_dir")"
  docker image tag "$image_id" "$rollback_tag"
  printf '  %s:\n    image: %s\n' "$service" "$rollback_tag" >> "$release_dir/rollback.images.yml"
  printf '%s %s %s\n' "$service" "$image_id" "$rollback_tag" >> "$release_dir/previous-images.txt"
done
printf '回滚材料目录：%s\n' "$release_dir"
BASH

通过： 三项旧镜像都有保留标签，旧源码 SHA、两个 Compose 和 .env 已备份。该目录包含 Secrets，仅在受控主机保存；另按组织备份流程加密备份。发布完成前不清理旧镜像。

3 收尾、停止旧应用并备份数据库

位置：业务主机 · /opt/ai-recruitment。 先进入维护窗口，阻止新上传、新面试和业务写入，等待在途队列任务、面试及录像收尾。准备兼容数据库版本的备份镜像（当前为 PostgreSQL 15），在停机前完成镜像获取：

bash
docker pull postgres:15-alpine

将下面 release_dir 替换为步骤 1 生成的实际目录。900 秒是显式停止超时示例，应按发布单调整。先停止旧应用，避免迁移过程中旧进程继续读写。

bash
bash <<'BASH'
set -eu
cd /opt/ai-recruitment || exit 1
release_dir=__FILL_EXISTING_RELEASE_DIRECTORY__
test "$release_dir" != __FILL_EXISTING_RELEASE_DIRECTORY__
test -f "$release_dir/previous-images.txt"
test ! -e "$release_dir/database.dump"
docker compose -f docker-compose.yml -f docker-compose.override.yml stop -t 900 web worker agent
docker compose --project-directory "$release_dir" --env-file "$release_dir/.env" \
  -f - run --rm -T backup <<'YAML'
services:
  backup:
    image: postgres:15-alpine
    environment:
      DATABASE_URL: ${DATABASE_URL:?数据库连接不能为空}
    networks:
      - arcinfra
    volumes:
      - ./:/backup
    entrypoint: ["sh", "-ec"]
    command:
      - |
        umask 077
        pg_dump --format=custom --no-owner --file=/backup/database.dump "$$DATABASE_URL"
        pg_restore --list /backup/database.dump >/dev/null
networks:
  arcinfra:
    external: true
    name: arc-infra_default
YAML
sha256sum "$release_dir/database.dump" > "$release_dir/database.dump.sha256"
BASH

通过： 旧应用已停，备份命令成功、文件非空且有校验和。备份目标使用步骤 1 保存的数据库连接，不能在本次普通升级中切换数据库。备份也由 Compose 读取 .env，保持引号与变量展开规则一致；内层 $$DATABASE_URL 用于把读取动作留到备份容器内。目录校验不能替代恢复演练；恢复能力须有已有演练记录。备份失败时不运行迁移，排障或按已确认的回退方案恢复旧应用。

一、项目概述

1.1 服务简介

系统覆盖简历上传与解析、人才库、招聘管理、智能上传及岗位推荐、简历筛选与评价、AI 语音面试、真人面试、候选人报告、工作区协作和外部通知。

当前运行技术栈：

  • Web：Node.js 22、TanStack Start、React 19、TanStack Router / Query、Vite / Nitro。
  • API：Hono、Better Auth；默认挂载在 Web 同进程的 /api 下。
  • 数据：PostgreSQL、Drizzle ORM；Mastra 使用同一数据库保存 AI 工作流和观测数据。
  • 异步任务：Redis / BullMQ、独立 Node.js Worker。
  • AI：阿里云百炼兼容接口、Mastra Agents / Workflows、Qwen OCR；语义检索使用 Embedding + Qdrant，岗位推荐使用 Rerank。
  • 实时音视频：LiveKit Server / Cloud；AI 面试由 Python LiveKit Agent 执行。
  • 语音链路：ElevenLabs Scribe v2 STT → DashScope LLM → MiniMax TTS。
  • 文件：S3 兼容存储；AI 录像与真人面试留底使用私有 RECORDING_R2_* 存储。
  • 集成：Google / 飞书登录、飞书机器人与文档、Google Sheets、Resend、Telegram、可选邮箱简历采集。

DATABASE_URL API、Worker、迁移、Mastra 数据与任务状态失联
REDIS_URL、RESUME_PARSE_QUEUE_PREFIX API、所有应用 Worker 入队后无人消费；不同数据库用户名也可能改变默认队列作用域
BETTER_AUTH_SECRET API 副本、提醒 Worker 会话或面试官邀请签名失败

LIVEKIT_* API、Agent、采样 Worker；对应 Server / Egress 项目 注册、发 Token、采样、录像及验签失败

存储和 LiveKit 的“一致”指向同一目标资源及相容的凭据、桶/房间项目和对象定位规则；内外网 Endpoint 可以不同，不要求所有网络地址文本完全相同。验证时应确认网络可达性和目标资源对应关系。

6.1 健康接口的真实检查范围

6.3 日志与访问

日志默认输出到 stdout/stderr，容器平台负责收集、轮转和保留。排查关键词包括：

readiness check failed、Dependency check failed、outbox unavailable、Interview media recording storage is not configured、livekit webhook signature verification failed、recording skipped、failed to start room composite egress。

生产日志应限制访问，避免复制 Secrets、完整简历、Webhook 请求凭据或原始 WebAuthn 返回到普通交付记录。RESUME_PARSE_LOG_STEPS 会增加解析内容相关日志，专项排查结束后关闭。当前有日志不代表应用已自动完成所有字段脱敏。

七、运维操作指南

7.1 常用操作

以下针对当前服务器，显式保留基础文件与运维覆盖文件：

bash
docker compose -f docker-compose.yml -f docker-compose.override.yml ps

docker compose -f docker-compose.yml -f docker-compose.override.yml logs --tail=200 -f web worker

docker compose -f docker-compose.yml -f docker-compose.override.yml restart worker

docker compose -f docker-compose.yml -f docker-compose.override.yml up -d --force-recreate web worker

restart 只重启已有容器，不会重新注入修改后的 env_file。运行变量变更使用更新 Secret 后重新创建容器；公开构建变量变更先重建镜像。重建 Web 会触发默认入口的迁移检查。

停机前停止新面试并等待在途任务。不要把 docker compose down 或强杀 Agent 当作零影响的日常维护。

7.2 发布与扩容

  • 当前根 Compose 是单副本起步声明，没有零停机发布保证。
  • Web 扩容前核对共享配置和数据库总连接预算。
  • Worker 扩容会增加普通解析/评价/索引总并发，需同时核对 AI 配额；历史解析并发单独受全局限制。
  • 提醒、媒体采样有数据库任务/租约协作，但必须观察失败补偿和重复消息边界。
  • Agent 发布为在途面试预留结束时间；LiveKit Server / Egress 升级另做组件兼容和真实媒体验收。
  • Web/Worker 与 Agent 均通过验收后，再撤销上一版本资源；保留上一版本镜像和配置。

7.3 配置变更与功能停用

  1. 确认本次变量属于构建、运行、历史残留或校验保留。
  2. 更新配置版本记录，仅登记变量名和 Secret 版本号。
  3. 构建变量重建；运行变量重建容器；跨服务同步配置。
  4. 验证对应业务链路与监控。
  5. 停用外部功能后再评估相关基础设施是否被其他功能或系统使用。

例如：关闭 NEXT_PUBLIC_ENABLE_INTERVIEW_RECORDING 不会关闭真人留底；关闭 HUMAN_INTERVIEW_MEDIA_ENABLED 不会删除既有留底；关闭向量索引不关闭 Rerank 调用。

7.4 索引与数据修复

仓库提供 backfill:jd-semantic-index、backfill:job-matching、backfill:resume-semantic-index 等源码脚本。其范围、输入和是否写入应以对应脚本当前参数为准。发布前评估已有岗位是否需要匹配画像/索引回填，记录运行范围与结果；不把全库回填作为每次启动的无条件操作。

8.2 应急回滚

先区分应用故障和数据库迁移兼容问题：

  1. 停止新任务/新面试，保留故障日志与发布版本。
  2. 评估上一版本是否兼容已经升级的数据库，特别是字段改名、时区类型和提醒机制。
  3. 兼容时，将生产声明切回上一版 Digest 和匹配的配置，再按就绪/业务流程验证。
  4. 不兼容时优先向前修复；如需恢复数据库，按第九章维护流程执行，不直接倒放迁移 SQL。
  5. 恢复服务后复核队列、会议、提醒、录像与留底，防止跨版本重复处理。

镜像回滚不自动回滚数据库。重新启动旧 Web 镜像也不能撤销已执行的迁移。恢复数据库会涉及备份后数据，需按实际故障处置授权和业务恢复目标执行。

9.2 数据库备份示例

在具有备份工具的受控终端中，由 Secret 管理系统注入正确的 DATABASE_URL。根 Compose .env 并不自动设置 Shell 变量：

bash
: "${DATABASE_URL:?请先由 Secret 管理系统注入目标数据库连接}"
pg_dump --format=custom --no-owner \
  --file="ai-recruitment-before-2056e99a.dump" \
  "$DATABASE_URL"

pg_restore --list ai-recruitment-before-2056e99a.dump >/dev/null
sha256sum ai-recruitment-before-2056e99a.dump

正式执行前必须确认连接串非空且目标正确；不在终端打印完整值。校验备份目录只是结构检查，仍需周期性做实际恢复演练。备份加密并保存至受控存储。

9.3 恢复步骤

  1. 停止写入和新任务，等待或明确终止在途面试及后台处理。
  2. 新建隔离的恢复数据库，避免直接覆盖当前生产库。
  3. 用兼容客户端恢复完整备份，核对 schema、行数、关键引用和迁移记录。
  4. 将隔离的同版本应用连接恢复库；使用隔离 Redis/队列前缀，避免测试实例消费生产任务或发送真实通知。
  5. 验证简历文件、AI 录像、长期留底对象均能按原 Key 找到。
  6. 完成恢复验收后，按批准的切换计划更新配置并启动 API / Worker / Agent。
  7. 复核待处理任务、已发提醒、会议状态与媒体租约；不将“数据库恢复成功”等同于端到端恢复。
bash
pg_restore --no-owner --dbname="<隔离恢复库连接>" ai-recruitment-before-2056e99a.dump

该命令为恢复阶段示例，目标必须是已经准备好的隔离数据库。涉及生产切换时采用实际变更流程。

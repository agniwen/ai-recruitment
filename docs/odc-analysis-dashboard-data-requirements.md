# ODC 分析看板：展示指标与流转数据采集需求（初稿）

> 来源：用户提供的「ATS-ODC 分析面板」示意图。本文只把图片表达的产品意图、展示指标和底层数据采集要求拆出来，不把示意图中的文字视为已经确认的最终口径。

## 1. 我对需求的理解

「ODC 分析」是一个以 ODC 为主要使用者或默认视角的招聘运营看板，但它不应只采集 ODC 操作产生的数据。

底层数据范围应覆盖工作区内所有参与招聘流转的角色，例如 ODC、HR、招聘负责人、面试官和管理员。角色是分析维度、数据权限和责任归属维度，不是数据采集过滤条件。所有候选人、岗位和流转事件都应完整记录，再根据当前用户权限、角色、招聘组和用人组织决定可见范围。

文档中需要特别区分两个容易混淆的概念：

- **工作区角色**：ODC、HR、管理员、自定义角色等，描述“谁在操作、谁能看什么”。
- **招聘岗位**：某个 JD/职位，描述“为哪个岗位招聘”。示意图里的“岗位筛选”“对接岗位数”指招聘岗位，不是工作区角色。

## 2. 示意图表达的页面结构

页面首页包含三个信息区域。其中后两个是图片明确标注的两块主面板；第一个是位于顶部的需求概览。

### 2.1 招聘需求概览

筛选项：

- 时间筛选，默认不限制。

展示信息：

- 提需日期。
- 期望到岗日期。
- 对接岗位数。
- 总 HC / 已到岗 / 空缺。

### 2.2 招聘整体进度 / 存量数据

筛选项：

- 时间筛选，默认不限制。
- 岗位筛选，默认不限制。

展示指标：

- 已关联简历。
- 当前待评估简历数。
- AI 面试。
- 面试环节数。
- Offer。
- 即将到岗，图片注明“读取 Offer 预入职字段”。
- 实际到岗。
- 淘汰 / 撤回。

交互要求：

- 指标卡支持鼠标悬停展示补充信息。
- 点击指标可跳转到简历库或对应业务列表。
- 跳转时同步当前时间、岗位及其他适用的筛选条件。

### 2.3 今日工作台 / 当日动态

筛选项：

- 时间筛选，默认今天。
- 岗位筛选，默认不限制。

展示指标：

- 已关联简历。
- 当前待评估简历数。
- 今日将开展 AI 面试数。
- 今日将开展面试环节数。
- 今日新增 Offer。
- 今日将到岗，读取 Offer 预入职日期。
- 今日实际到岗。
- 今日淘汰 / 撤回。

补充展示：

- 在“今日将开展 AI 面试数”下，用不同颜色展示未来 3 天的 AI 面试数。
- 在“今日将开展面试环节数”下，用不同颜色展示已面试、当前面试中、即将面试；图片要求根据面试时间和已完成面试情况统计。
- 在“今日将到岗”下，用不同颜色展示未来 3 天预计到岗人数。

## 3. 为看板必须采集的原始数据

下面列的是流转过程中要保存的原始事实。看板数字应由这些事实计算，不应在业务操作时直接写入一套独立的“看板数字”。

### 3.1 通用分析维度

每条招聘事实或流转事件至少应能关联到：

| 字段                            | 用途                                                    |
| ------------------------------- | ------------------------------------------------------- |
| 工作区 ID                       | 多租户隔离                                              |
| 用人组织 ID                     | 数据权限、组织维度统计                                  |
| 部门 ID                         | 部门维度统计                                            |
| 招聘岗位 ID、岗位编码、岗位名称 | 岗位筛选和下钻                                          |
| 候选人 / 简历记录 ID            | 候选人去重和下钻                                        |
| 操作人 ID                       | 追踪由谁完成操作                                        |
| 操作人当时的工作区角色          | 按 ODC、HR 等角色分析历史工作量；不能只读取用户当前角色 |
| 招聘组 / 责任人 ID              | 责任归属和可见范围                                      |
| 事件发生时间                    | 时间筛选和当日动态                                      |
| 数据来源                        | 手工、Google Sheet、Agent、批量导入、邮件采集、API 等   |

关键原则：如果一个用户后来从 HR 改成 ODC，历史事件仍应保留其操作发生时的角色，不能把旧数据全部解释成新角色产生的数据。

### 3.2 招聘需求与岗位数据

| 必须记录的数据              | 支持的展示                                                                 |
| --------------------------- | -------------------------------------------------------------------------- |
| 提需日期                    | 需求概览、按时间筛选岗位需求                                               |
| 期望到岗日期                | 需求时效和到岗计划                                                         |
| HC 总数                     | 总 HC                                                                      |
| 已到岗人数                  | 已到岗                                                                     |
| 空缺 / 缺口人数             | 空缺；建议统一计算为 `max(HC - 已到岗, 0)`，人工缺口字段只作校验或业务覆盖 |
| 已发 Offer 待入职人数       | Offer 到到岗之间的存量                                                     |
| 岗位状态                    | 过滤关闭、暂停、已招满等岗位                                               |
| 岗位创建、变更、关闭时间    | 还原某个历史时间点的岗位存量                                               |
| 岗位负责人 / 对接人及其角色 | 统计 ODC 或其他角色对接的岗位数                                            |

仅保存岗位当前的 HC、缺口和已到岗值，无法准确回答“上个月某天当时有多少空缺”。如果时间筛选需要历史回看，必须补充岗位需求变更历史或每日快照。

### 3.3 简历与岗位关联

| 必须记录的数据                     | 支持的展示                            |
| ---------------------------------- | ------------------------------------- |
| 候选人 / 简历 ID                   | 唯一候选人计数                        |
| 岗位 ID                            | 按岗位过滤                            |
| 关联时间                           | 今日已关联、区间新增关联              |
| 关联来源                           | 上传、简历池导入、邮件、Agent、API 等 |
| 关联操作人、当时角色               | 按角色统计工作量                      |
| 解除关联或换岗时间、原岗位和新岗位 | 避免只看当前岗位导致历史统计失真      |

“已关联简历”建议默认统计去重后的候选人数量，而不是关联操作次数。若业务还需要衡量工作量，可另设“关联次数”。

### 3.4 简历评估

| 必须记录的数据                               | 支持的展示                   |
| -------------------------------------------- | ---------------------------- |
| 评估状态：待评估、评估中、通过、不通过、失败 | 当前待评估简历数             |
| 进入待评估时间                               | 今日新增待评估、等待时长     |
| 评估开始时间                                 | 评估效率                     |
| 评估完成时间                                 | 当日完成量和处理时长         |
| 评估人、当时角色                             | 按 ODC、HR 等角色统计        |
| 评估方式                                     | 人工、AI、人工复核           |
| 评估结果变更历史                             | 避免只保存最终状态而丢失过程 |

“当前待评估”是一个存量指标，通常应以候选人的当前状态计算；时间筛选是限制岗位/候选人范围，还是回看某一历史时点，需要产品进一步确认。

### 3.5 AI 面试

| 必须记录的数据                             | 支持的展示             |
| ------------------------------------------ | ---------------------- |
| AI 面试轮次 ID、候选人 ID、岗位 ID         | 去重和下钻             |
| 计划开始、计划结束时间                     | 今日及未来 3 天安排    |
| 实际开始时间                               | 当前面试中             |
| 实际完成时间                               | 已面试、当日完成量     |
| 状态：待开始、进行中、中断、已完成、已取消 | 分色状态展示           |
| 取消时间、取消原因                         | 排除取消场次、分析流失 |
| 发起人、发起人当时角色                     | 角色工作量             |

“AI 面试”需要明确是统计候选人数、面试轮次数还是实际会话数。建议默认以面试轮次计数，同时保留候选人去重口径。

### 3.6 真人面试 / 其他面试环节

| 必须记录的数据                       | 支持的展示                  |
| ------------------------------------ | --------------------------- |
| 面试环节 / 轮次 ID、名称、顺序       | 面试环节数                  |
| 面试类型                             | 区分真人复面、HR 面、终面等 |
| 计划开始时间                         | 即将面试、今日安排          |
| 实际开始时间                         | 当前面试中                  |
| 实际结束 / 完成时间                  | 已面试                      |
| 状态：待开始、进行中、已完成、已取消 | 分色状态展示                |
| 面试官及其角色                       | 面试官维度分析              |
| 结果、评分、评价提交时间             | 判断面试是否真正完成        |
| 取消时间和原因                       | 排除取消场次                |

图片把“AI 面试”和“面试环节数”分开，因此初步按“AI 面试轮次”和“真人/后续面试轮次”分别统计。是否包含笔试或其他环节需要确认。

### 3.7 Offer 与预计到岗

| 必须记录的数据                                     | 支持的展示                       |
| -------------------------------------------------- | -------------------------------- |
| Offer ID、版本号                                   | 去重和追踪改版                   |
| 创建时间                                           | 今日新增 Offer（若采用创建口径） |
| 发出时间                                           | 今日发出 Offer（若采用发送口径） |
| 状态：草稿、已发送、已接受、已拒绝、已过期、已替代 | Offer 存量和转化                 |
| 候选人响应时间                                     | Offer 转化时长                   |
| Offer 预入职 / 预计到岗日期                        | 今日将到岗、未来 3 天将到岗      |
| Offer 创建人、发送人及其当时角色                   | 角色工作量                       |

同一候选人可能有多个 Offer 版本。看板应默认只统计当前有效版本，不能把旧版和新版重复计数。

### 3.8 实际到岗

| 必须记录的数据           | 支持的展示                 |
| ------------------------ | -------------------------- |
| 实际到岗日期             | 今日实际到岗、区间实际到岗 |
| 到岗确认时间             | 审计和时效                 |
| 到岗岗位、部门、用人组织 | 按组织和岗位统计           |
| 确认人、确认人当时角色   | 责任追踪                   |
| 原预计到岗日期           | 计算按期、提前、延期到岗   |

实际到岗应是独立、明确的业务事实。不能仅因为 Offer 已接受或预计到岗日期已到，就自动视为实际到岗。

### 3.9 淘汰、撤回与归档

| 必须记录的数据                         | 支持的展示                                             |
| -------------------------------------- | ------------------------------------------------------ |
| 结案结果：淘汰、候选人撤回、到岗、归档 | 淘汰 / 撤回和最终转化                                  |
| 结案时间                               | 今日及区间淘汰 / 撤回                                  |
| 结案前所在阶段                         | 分析在哪个环节流失                                     |
| 标准化原因分类                         | 技能不匹配、文化不符、薪资分歧、候选人放弃、岗位招满等 |
| 备注                                   | 业务复盘                                               |
| 操作人、操作人当时角色                 | 角色工作量和审计                                       |
| 重新激活时间、原因、恢复阶段           | 防止结案后重新进入流程造成重复统计                     |

“淘汰 / 撤回”建议分别保留原始结果，在卡片上可以合并展示，但下钻和分析时应能拆开。

### 3.10 候选人阶段流转事件

为了支持任意时间区间和历史回放，每次阶段变化都应追加一条不可变事件：

| 字段                      | 说明                             |
| ------------------------- | -------------------------------- |
| 候选人 ID、岗位 ID        | 事件主体                         |
| 原阶段、目标阶段          | 流转方向                         |
| 原结果、目标结果          | 是否进入终态                     |
| 发生时间                  | 时间分析                         |
| 操作人 ID、操作人角色快照 | 责任与角色分析                   |
| 招聘组、用人组织快照      | 历史权限和组织归属               |
| 原因 / 备注               | 淘汰、撤回、重新激活等原因       |
| 来源                      | 页面操作、Agent、系统自动化、API |

当前状态表用于快速查询“现在在哪里”，事件表用于回答“什么时候从哪里到了哪里”。两者都需要保留。

## 4. 指标口径初稿

| 看板指标         | 建议初始口径                                                        |
| ---------------- | ------------------------------------------------------------------- |
| 对接岗位数       | 筛选范围内、当前有效且分配给可见招聘组/责任人的去重岗位数           |
| 总 HC            | 岗位 HC 求和                                                        |
| 已到岗           | 实际到岗事实去重候选人数；岗位表中的已到岗数可作外部同步校验        |
| 空缺             | `max(总 HC - 实际到岗人数, 0)`；是否扣除已接受 Offer 待到岗需确认   |
| 已关联简历       | 与筛选岗位有关联的去重候选人数                                      |
| 当前待评估简历数 | 当前处于简历筛选阶段且评估结果仍为空的去重候选人数                  |
| AI 面试          | 符合时间范围、已安排 AI 面试的去重候选人数                          |
| 面试环节数       | 符合时间范围的真人/后续面试轮次数                                   |
| Offer            | 当前有效且已发送的逻辑 Offer 数；同一候选人同一岗位的改版不重复计数 |
| 今日新增 Offer   | 首次成功发送时间落在今天的逻辑 Offer 数                             |
| 即将到岗         | 当前有效 Offer 的预入职日期落入筛选区间的去重候选人数               |
| 实际到岗         | 实际到岗日期落入筛选区间的去重候选人数                              |
| 淘汰 / 撤回      | 结案时间落入筛选区间且结果为淘汰或撤回的去重候选人数                |

## 5. 与当前系统数据的初步对照

### 5.1 已有基础数据

- 岗位已有提需日期、期望到岗日期、HC、缺口、已发 Offer 待入职数、已到岗数。
- 候选人已有当前招聘阶段、最终结果、结案时间和结案原因/到岗细节。
- 候选人阶段变更已有审计日志，能记录原阶段、目标阶段、原结果、目标结果和操作人。
- AI 面试已有计划时间、实际开始时间和状态。
- 真人面试已有轮次、计划时间、完成/取消时间、状态、结果、评分和评价。
- 真人面试会议已有计划、开始、结束、取消时间和状态。
- Offer 已有多版本、创建时间、发送时间、响应时间、状态和预计入职日期。

### 5.2 为可靠分析建议补齐的数据

- 所有关键事件的**操作人角色快照**，不能只依赖用户当前角色。
- 候选人与岗位的**关联历史**，包括关联、换岗和解除关联时间。
- 岗位 HC、缺口、预计到岗等字段的**变更历史或每日快照**。
- AI 面试的显式完成时间和取消记录，避免用更新时间猜测。
- 真人面试轮次的实际开始时间；会议时间不能完全替代每位候选人每一轮的开始时间。
- Offer 创建人、发送人等关键责任人及其角色快照。
- 实际到岗作为独立业务事件的确认时间和确认人。
- 统一的事件来源字段，区分人工、Agent、API 和系统自动化。

## 6. 实现前必须确认的口径

1. “时间筛选”对存量卡片表示“当前状态下按创建日期过滤”，还是“回看某个历史时点的存量”？后者必须依赖事件历史或快照。
2. “已关联简历”统计去重候选人数，还是简历与岗位的关联次数？
3. “当前待评估”已确认：统计当前处于简历筛选阶段且尚无评估结果的候选人，不包含已评估但尚未推进、AI 面试待完成或其他人工复核状态。
4. “AI 面试”已确认：统计去重候选人数，不统计轮次数或实际会话数。同一候选人在同一统计范围内有多次 AI 面试，只计 1 人。
5. “面试环节数”是否只统计真人面试，是否包含笔试和其他自定义环节？
6. “今日新增 Offer”已确认按发送时间统计。建议使用同一候选人 × 同一岗位下逻辑 Offer 的“首次成功发送时间”：草稿不计入，发送失败不计入，修改版本和重复发送不重复计数；候选人接受时间另用于 Offer 接受和转化指标。
7. “空缺”是否仅等于 HC 减实际到岗，还是还要扣除已接受 Offer 待到岗人数？
8. “即将到岗”是否只统计已接受 Offer，还是所有带预入职日期的有效 Offer？
9. “今日实际到岗”由谁确认，是否允许修改、撤销以及补录历史日期？
10. “淘汰 / 撤回”在卡片上合并后，下钻页面是否默认拆分原因和发生阶段？
11. ODC 默认可看全工作区，还是仍受招聘组、用人组织和岗位范围约束？
12. 点击指标跳转后，是进入候选人管理、面试日程、Offer 列表，还是统一进入简历库并附带筛选参数？

## 7. 建议的采集原则

- **全角色采集、按权限展示**：不因页面名叫 ODC 分析而过滤非 ODC 数据。
- **事实优先**：记录业务事件和时间，再由查询计算指标。
- **当前状态 + 历史事件并存**：当前状态服务列表，事件历史服务分析和审计。
- **角色和组织保留快照**：人员换角色、换组后，历史统计不应改变。
- **候选人和 Offer 去重**：同一候选人多轮面试、多版 Offer 要有明确的统计粒度。
- **所有卡片可解释、可下钻**：每个数字都能跳转到组成该数字的明细记录，并继承筛选条件。

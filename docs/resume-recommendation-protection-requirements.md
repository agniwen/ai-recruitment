# 简历推荐保护期功能需求文档

版本：V0.8 暂时隐藏继续推荐入口\
日期：2026-10-23\
适用系统：AI Recruitment Copilot\
阅读对象：业务负责人、产品、设计、研发、测试

在同一工作区内，一名招聘人员首次有效推荐候选人后，获得默认 15 天的推荐保护期。保护期内，本人可以继续向不同用人组织推荐该候选人，其他推荐人的上传默认拦截。系统在解析后、JD 分析前检测，命中后保留本次上传记录，仅在“候选人管理 → 全部候选人”展示，不产生有效推荐，也不进入 AI 评价审核等招聘阶段。保护期时长通过参数页面维护。

当前展示范围（2026-10-23 确认）：列表与候选人详情均隐藏“继续推荐”按钮，不展示二次确认窗口及相关操作提示；保留保护标签、摘要和“查看保护详情”。已实现的继续推荐组件及后端接口暂时保留。下文有关继续推荐的流程描述属于预留能力，不作为当前界面开放范围；无岗位记录的后续推荐路径仍需在重新开放前补齐。

本文中的“质保期”统一称为“推荐保护期”，表示推荐归属保护，不涉及入职后的服务质保、佣金结算或离职补人。

本轮实现范围补充：在保护摘要中增加“继续推荐”。本次上传人或具备简历创建权限的工作区管理员二次确认后沿用记录已保存的岗位和组织，仅放行当前记录并启动后续分析。保护期内确认不更换原保护人、不延长原周期、不自动放行其他记录；到期确认重新执行正常保护校验和建档。受保护记录的详情及时间线显示保护状态，隐藏 AI 评分和招聘阶段推进操作，确认成功后恢复正常流程。确认操作写入既有候选人操作记录，不新增数据库结构。下文默认拦截规则均以未显式确认继续推荐为前提。界面不显示匹配依据、解析或缓存细节。实施决策及上线步骤见 [ADR 0024](adr/0024-resume-recommendation-protection.md) 和 [上线说明](resume-recommendation-protection-rollout.md)。

## 一 需求背景与原始通知解读

当前 HR 使用的 TG 通知，包含收到简历、重复匹配结果、匹配依据，以及此前推荐的组织、人员和时间。截图同时出现了“简历库已有此简历，不再收录”和“已记录新推荐信息”，反映出两类不同记录：简历内容可以复用，推荐行为仍需要保留。

平台需要在已有查重能力上补充推荐归属和时间规则，使招聘人员能够在提交时明确知道谁已推荐、推荐给哪些组织、保护期何时结束，减少重复推荐和归属争议。

截图只作为通知内容与历史记录展示的参考。截图没有说明保护期算法，也没有提供“保护期内禁止提交”的规则；本需求的拦截规则以本次沟通确认的第二节为准。

## 二 已确认的业务规则

| 事项               | 确认结果                                             |
| ------------------ | ---------------------------------------------------- |
| 默认时长           | 15 天，后续可在参数页面配置                          |
| 检测范围           | 同一工作区内，覆盖所有用人组织                       |
| 跨组织场景         | A 推荐给组织甲后，B 在保护期内推荐给组织乙，同样拦截 |
| 保护对象           | 具体推荐人，不是整个招聘团队                         |
| 同团队场景         | 同一招聘团队的其他成员上传也默认拦截，显式确认规则一致       |
| 命中后的处理       | 默认禁止继续提交；本次上传人或具备相应权限的工作区管理员可显式确认继续推荐     |
| 同一推荐人再次推荐 | 可以推荐到其他组织，保护期不重新计算                 |
| 计时依据           | 以本轮首次有效推荐时间为准                           |
| 重复提示内容       | 展示历史推荐时间、组织名称和推荐人；组织可能有多个   |
| 被拦截记录的位置   | 本次被保护期拦截的上传仅在候选人管理的“全部”显示，不进入其他招聘阶段 |
| 与疑似重复的关系   | 两项独立业务判断，可复用简历向量及历史候选记录召回；重复标记不代表保护期拦截 |
| 界面变更边界 | 只增补保护期状态、提示及必要动作；原有卡片资料、简历入口、编辑和更多菜单沿用现状，新增提示不展示解析过程 |

下文将这些规则作为首期范围。身份判定、推荐人的取值、参数变更及历史数据处理中的建议方案，在相应章节标明，仍需评审确认。

## 三 系统现状与能力差距

以下现状来自当前仓库的领域文档和代码，适用于需求及研发评审；线上部署状态需在实施前另行核对。

| 业务能力       | 当前系统情况                                                                       | 本需求需要补充的能力                                                         |
| -------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 工作区隔离     | 工作区是招聘数据和设置的隔离边界；底层 `organizationId` 表示工作区                 | 保护期在工作区内生效，保持工作区隔离                                         |
| 招聘组织       | 已有招聘组、部门/中心（来源）、用人组织、部门和岗位                                | 本文“推荐到的组织”按用人组织解释，不与工作区或招聘组混用                     |
| 简历暂存与推荐 | 人才库是推荐前的暂存区域；加入“招聘”后形成简历记录                                 | 明确上传、解析、AI 匹配与有效推荐的区别                                      |
| 多组织推荐     | 人才库导入支持多个目标；智能推荐可选择多个岗位，分别创建简历记录                   | 保留每次推荐的目标明细，并在提示中汇总多个组织                               |
| 查重           | 已有语义检索及结构化信息重排，返回疑似重复等级、匹配依据和历史记录信息             | 增加可靠的同人识别、保护人、保护时间和提交拦截                               |
| 同上传人处理   | 当前语义查重会排除当前上传人创建的记录                                             | 保护期判定仍需查出本人的历史记录，用于找到既有保护周期，防止再次推荐重置计时 |
| 重复展示       | 已有疑似重复弹窗，展示上传人、用人组织、来源、部门等上下文；部分流程提供“仍然继续” | 保护期冲突展示归属和时间并默认拦截；通过独立确认操作继续推荐                 |
| 推荐人         | 简历记录主要保存创建人和导入人，查重界面展示上传人；未见独立的推荐人身份字段       | 明确实际推荐人与操作人的关系，不能直接把所有上传人都视为推荐人               |
| 历史时间       | 已有创建时间、人才库导入时间等；批量上传会先创建待解析占位记录                     | 单独定义有效推荐时间，不能统一使用记录创建时间起算                           |
| 参数配置       | 工作区已有“公司信息与话术”；平台管理已有“面试参数”，含真人面试锁定时长             | 增加推荐保护期参数，确定维护入口及配置权限；与真人面试锁定分开               |
| TG 通知        | 已有 AI 评价待审批等 TG 通知能力                                                   | 平台拦截及历史展示为首期必需；新增 TG 保护期通知不列为首期必需               |

当前不同入口的处理并不一致：单条创建会查询并保存疑似重复结果后继续创建；人才库导入存在查重及强制继续分支；智能推荐提交会按所选岗位创建记录。保护期需要统一的服务端规则，不能只修改一个上传弹窗。

当前语义查重依赖解析结果及向量服务；未启用或缺少解析结果时可返回空列表，部分异常也会返回空列表。此行为不能直接作为“无保护期冲突”的依据。

## 四 目标与首期范围

### 业务目标

1. 在推荐提交时识别同一候选人已有的有效保护期。
2. 阻止其他推荐人在保护期内向任何用人组织提交同一候选人。
3. 提供可追溯的推荐历史，回答“谁、何时、推荐给哪些组织”。
4. 支持维护保护期天数，避免将 15 天写死在业务流程中。

### 首期包含

- 推荐人身份、有效推荐时间及保护周期的记录。
- 单条推荐、批量推荐、人才库导入及智能推荐提交的保护期校验。
- 保护期冲突提示、提交拦截及必要的检测结果记录。
- 简历详情中的推荐历史与保护状态展示。
- 保护期时长参数维护。
- 历史记录是否可以参与检测的上线处理规则。

### 首期不包含

- 跨工作区查重及跨工作区推荐保护。
- 推荐归属转移、提前解除保护、保护期内审批放行。
- 招聘佣金、入职质保、团队业绩结算。
- 建设独立的 TG 简历接收机器人或同步截图所用系统的全部历史记录。
- 自动合并、覆盖或删除已有简历和推荐记录。

## 五 业务概念与推荐人身份

| 概念         | 定义                                                                     |
| ------------ | ------------------------------------------------------------------------ |
| 候选人       | 简历对应的自然人，同一人可以有不同文件版本和多条岗位简历记录             |
| 推荐人       | 本次推荐归属的具体人员，也是保护期保护的对象                             |
| 操作人       | 实际在平台上传或提交的登录成员，可能与实际推荐人不同                     |
| 用人组织     | 接收推荐的业务组织，使用现有用人组织数据，不以自由文本建立新组织         |
| 有效推荐     | 候选人身份可判定、推荐人和目标组织明确、校验通过且推荐记录提交成功的行为 |
| 保护周期     | 从本轮首次有效推荐开始，到保护截止时间结束的一段归属保护                 |
| 重复推荐尝试 | 其他人对受保护候选人的提交尝试；不属于成功推荐，不产生新保护周期         |

**推荐人取值建议，待确认：**首期使用当前登录工作区成员作为推荐人，平台自动填写，不允许普通成员任意改成他人。操作人仍单独保留。若业务存在“助理或机器人代实际推荐人提交”，则需要在首期确定被代理人员的可选范围、身份凭据及代推荐权限。

截图同时出现一名“推荐方”及一名“简历推荐人”，因此这项取值必须在开发前确认。自由填写的 TG 昵称、简历来源说明、推荐语均不能直接作为保护归属的唯一标识。

招聘组作为历史上下文保留。人员更名、调组或离职不应自动改写历史推荐人，也不应使保护期自动重置或失效。

## 六 保护期判定与时间规则

### 判定顺序

1. 确定当前工作区、当前推荐人及候选人身份。
2. 查找本工作区该候选人的推荐历史及当前保护周期，不能只查询当前人的可见简历列表。
3. 无有效保护周期时，允许提交；提交成功后开启新周期。
4. 存在有效保护周期且当前人为受保护推荐人时，允许向有权限的目标组织继续推荐，沿用原周期。
5. 存在有效保护周期且当前人为其他推荐人时，返回保护期冲突，禁止提交。
6. 检测未完成或异常时，显示具体状态，不得显示“查重通过”。

### 计时口径建议

- 使用服务端时间起算，15 天按连续 15 × 24 小时计算，不按工作日或自然日零点截断。
- 保护开始时间为首次有效推荐的提交成功时间，不是文件上传、AI 匹配完成或审批通过时间。
- 保护截止时间 = 保护开始时间 + 当次生效的保护期天数。
- 有效区间为“开始时间 ≤ 当前时间 < 截止时间”；到达截止时间即过期。
- 时间存储使用统一时间基准，页面明确按北京时间（Asia/Shanghai）展示到分钟，边界判定保留完整精度。
- 同一推荐人后续向更多组织推荐，只增加历史明细，不延长保护截止时间。
- 其他人被拦截的尝试、重复点击、接口重试、解析重试和重新评分均不延长保护期。
- 保护到期后，下一次有效推荐开启新周期，可由原推荐人或其他推荐人取得。
- 建议归档、淘汰、暂停招聘及删除岗位均不自动提前解除保护；提前解除不在首期范围。

上述连续小时、期满后新周期及生命周期处理为建议口径；首次有效推荐起算、本人再次推荐不重算已经业务确认。

### 判定示例

假设推荐人 A 在 2026-10-01 10:00 首次有效推荐候选人 C，保护期为 15 天，则截止时间为 2026-10-16 10:00。

| 后续行为                                    | 预期结果                             |
| ------------------------------------------- | ------------------------------------ |
| A 在 10 月 10 日向组织乙推荐 C              | 允许；截止时间仍为 10 月 16 日 10:00 |
| B 在 10 月 10 日向组织甲推荐 C              | 拦截                                 |
| B 在 10 月 10 日向从未接收过 C 的组织丙推荐 | 拦截                                 |
| A 的同团队成员 B 在保护期内推荐 C           | 拦截                                 |
| B 在 10 月 16 日 09:59 推荐 C               | 拦截                                 |
| B 恰好在 10 月 16 日 10:00 成功推荐 C       | 按建议口径开启 B 的新保护周期        |
| B 在另一工作区推荐 C                        | 本工作区保护期不参与该次判定         |

## 七 同一候选人的识别

保护针对候选人及其推荐归属。更换文件名、更新简历版本、更换岗位、来源渠道或推荐语，不应使同一个人绕过保护期。

疑似重复与推荐保护期是两项独立业务判断：疑似重复用于系统内展示风险，推荐保护期用于决定本次推荐是否允许进入后续流程。已过保护期的候选人仍可保留疑似重复标记，隐藏或处理重复标记也不会解除有效保护。

两项业务复用同一套简历内容向量及历史记录召回，不分别建设“疑似重复向量”和“保护期向量”。向量模型、维度和版本需兼容；时间、推荐人、组织和招聘阶段从数据库关联，不写进向量。历史候选记录召回后分别生成疑似重复结果及保护期判断，避免各调用一次相同的 Embedding。保护期判断不能直接复用经过界面展示规则过滤后的重复列表，需覆盖被同上传人排除及返回数量限制遗漏的记录。

| 识别情况                                       | 处理要求                                             |
| ---------------------------------------------- | ---------------------------------------------------- |
| 同一份简历文件内容一致                         | 可作为相同简历的强证据，并关联历史推荐               |
| 文件不同，但规范化联系方式与姓名等身份信息一致 | 综合判断是否为同一候选人，需排除明显冲突             |
| 经历、技能、学校等语义相似                     | 返回疑似重复及依据，不可仅凭相似度分数认定同一人     |
| 只有姓名一致或文件名一致                       | 不足以认定同一人                                     |
| 联系方式不同、身份信息冲突                     | 明确展示冲突，不自动合并或改写身份                   |
| 无解析结果、服务异常或无法完成必要检测         | 标记检测未完成，允许保存待处理资料，暂不完成有效推荐 |

已确认同一候选人且处于他人保护期内时默认拦截，普通疑似重复弹窗的“仍然继续”不能绕过保护。放行必须使用保护摘要中的“继续推荐”，沿用当前记录已保存的岗位并显式确认，由服务端校验身份、权限、候选人及保护状态后仅放行当前记录。

实施时必须覆盖尚未完成向量索引的新推荐，不能依靠异步语义检索作为唯一判定来源。现有默认返回数量限制也不能导致漏掉有效保护周期。

## 八 各推荐入口的功能要求

| 入口或动作                     | 检测与计时要求                                                     |
| ------------------------------ | ------------------------------------------------------------------ |
| 单条简历上传并推荐             | 解析及目标确认后预检测，提交时再次校验，成功提交才开始计时         |
| 批量上传到招聘                 | 逐候选人检测；待解析占位记录不计为有效推荐，不得先成功推荐再补拦截 |
| 私有或公共人才库加入招聘       | 在导入提交前检测，保护期校验不受现有强制导入参数影响               |
| 智能推荐选择岗位后提交         | AI 生成岗位建议不计时；用户提交所选目标时检测并建立推荐历史        |
| 单次向多个组织或岗位推荐       | 对候选人先统一检测，允许后保存各目标明细，共享同一保护周期         |
| 仅上传到人才库或邮箱导入人才库 | 属于资料收集，不开始保护期；后续正式推荐时检测                     |
| 修改现有记录的岗位或组织       | 若属于向新目标的实际推荐，必须经过同一校验；不能通过编辑绕过       |
| 历史导入及后台任务             | 必须有明确的历史录入规则，不能将技术导入时间自动当成新的推荐时间   |

同一候选人在一次提交中选择多个目标时，保护期冲突会阻止该候选人的全部目标，不能部分漏写。不同候选人之间建议独立处理；批量结果分别展示成功、被保护期拦截、检测失败或待处理，避免一个冲突导致其他候选人重复提交。

对异步批量入口，保留上传和解析进度展示，但有效推荐、保护周期与后续流程的开放必须在校验成功之后。检测失败的占位资料不得触发有效推荐通知、计入成功推荐数量或自动推进招聘流程。

共同顺序为：上传及解析 → 共用向量召回与身份核对 → 分别得到疑似重复结果、保护期判断 → 保护期决定是否允许后续推荐及 JD 分析。命中他人有效保护期后，保存的是本次上传及拦截记录，不是成功推荐。该记录在“全部候选人”可见，以独立的受理状态展示，不挂入 `ai_review` 等招聘阶段；物理数据模型在实施时确定。

## 九 保护期冲突提示与历史展示

### 冲突提示

标题：**该候选人处于推荐保护期，暂不能重复推荐**。

提示必须包含：候选人姓名、受保护推荐人、本轮首次有效推荐时间、保护截止时间，以及历史推荐的组织、时间和人员。推荐团队作为补充信息展示。

示例内容使用虚构人员和组织：

> 候选人：张某\
> 受保护推荐人：王某（招聘一组）\
> 本轮首次推荐：2026-10-01 10:00\
> 保护截止：2026-10-16 10:00（北京时间）\
> 已推荐组织：组织甲、组织乙\
> 该候选人仍处于王某的推荐保护期。本次上传已保留，仅在全部候选人展示，尚未进入 JD 分析与招聘流程。

| 历史推荐时间     | 用人组织 | 推荐人 | 所属招聘组 | 保护状态         |
| ---------------- | -------- | ------ | ---------- | ---------------- |
| 2026-10-10 14:30 | 组织乙   | 王某   | 招聘一组   | 当前保护周期     |
| 2026-10-01 10:00 | 组织甲   | 王某   | 招聘一组   | 当前保护周期起点 |
| 2026-08-01 09:00 | 组织丙   | 李某   | 招聘二组   | 历史已过期       |

组织摘要按组织去重，用文字展示多个名称；历史明细保留每次有效推荐的时间和人员，不将多次推荐压成一个模糊时间。默认突出当前保护周期，历史记录可展开或分页查看。

上传检测命中后的提示提供“查看保护详情”和“返回全部候选人”。列表与详情中的按钮按第十六节状态表执行。已有简历详情按访问权限提供查看入口。命中有效保护期时仅向有权限的本次上传人或工作区管理员提供“继续推荐”，点击后进入确认窗口。

### 简历详情

增加推荐历史及保护信息：当前受保护推荐人、保护开始与截止时间、当前周期使用的天数、是否已过期，以及历史推荐明细。倒计时仅辅助展示，提交结果以服务端判定为准。

### 权限要求

具有推荐权限的成员，应能够获知冲突所必需的最小摘要，包括推荐时间、用人组织和推荐人，即使其不能查看对方完整简历。这项跨招聘组摘要访问需要明确授权，不随之授予完整简历、联系方式、评价报告或附件访问权限。

完整详情、文件和其他业务数据继续遵守现有招聘组、汇报关系、ODC 和 SSC 等访问规则。所有查询、提示及链接继续限制在当前工作区。

## 十 参数页面

字段名称：**简历推荐保护期**。单位：天。默认值：15。

| 项目       | 要求及建议                                                                 |
| ---------- | -------------------------------------------------------------------------- |
| 参数值     | 必填正整数；空值、0、负数和小数不允许保存；最大值由业务评审确定            |
| 参数作用域 | 建议按工作区维护，同一工作区所有招聘组、推荐人和用人组织统一使用           |
| 页面位置   | 建议首期在现有工作区配置页增加“招聘规则”区域；是否单设“参数设置”入口需确认 |
| 维护权限   | 建议复用工作区全局配置的读取及更新权限，不向普通推荐人开放修改             |
| 保存反馈   | 显示保存成功或失败，失败不覆盖有效配置；记录修改人、时间及旧值/新值        |
| 生效范围   | 建议只影响保存后新开启的保护周期，当前周期保留原有天数和截止时间           |

配置修改示例：10 月 5 日将 15 天改为 30 天，10 月 1 日已开始的周期仍按 15 天到期；10 月 5 日修改后新开启的周期使用 30 天。原推荐人在旧周期内追加组织，仍沿用旧周期，不改成 30 天。

字段说明建议：

> 从本轮首次有效推荐开始计算。在保护期内，其他推荐人不能向本工作区任何用人组织推荐同一候选人；原推荐人新增推荐组织不会延长保护期。修改天数仅影响新开启的保护周期。

现有平台“面试参数”中的真人面试锁定时长管理另一项业务，不直接复用其字段或计时规则。若实际希望由平台管理员统一维护全平台天数，需要另行确认配置作用域。

## 十一 必须保留的业务信息

以下是逻辑信息要求，不预设数据库表名或物理存储方案。

| 信息类别   | 必需内容                                                   |
| ---------- | ---------------------------------------------------------- |
| 候选人关联 | 当前工作区、用于关联同一候选人的身份依据、关联简历记录     |
| 推荐归属   | 推荐人稳定标识及名称快照、操作人、推荐时的招聘组上下文     |
| 推荐目标   | 用人组织标识和名称快照、岗位信息（如有）、推荐来源         |
| 推荐时间   | 有效推荐时间；历史补录时另记录入时间及时间依据             |
| 保护周期   | 受保护推荐人、首次有效推荐、保护开始/截止时间、生效天数    |
| 检测结果   | 本次请求、检测时间、检测状态、匹配依据、冲突周期及处理结果 |

成功推荐历史与被拒绝的推荐尝试分开记录。被拒绝的尝试不得成为新的历史成功推荐，也不得改变既有保护人和时间。

名称变更后历史仍能解释当时的组织与人员。既有简历记录被归档或删除时，不能顺带删除仍在生效的保护依据；历史保留及个人信息删除需按系统既有规则设计。

## 十二 一致性与异常处理

1. 最终校验必须在服务端执行，覆盖 Web 集成后端和独立 Hono 后端，以及后台实际写入推荐的路径。
2. 两人同时推荐同一候选人时，只允许一个人成为该轮保护人；另一个人获得冲突结果。校验和有效推荐写入之间不得留下并发绕过窗口。
3. 相同请求重复提交、网络重试或任务恢复，只返回同一次业务结果，不重复生成推荐、延长保护或发送成功通知。
4. 用户预检测通过后，如果他人先提交成功，最终提交仍应拦截，并刷新冲突信息。
5. 解析或必要查重服务不可用时，返回“检测未完成，请稍后重试”，允许资料保持待处理，禁止伪装成无重复的成功推荐。
6. 超过有效期的普通重复记录可以继续作为历史提示，但不能仅因“曾经推荐过”无限期拦截。
7. 任一入口的强制创建、强制导入或旧版客户端参数，都不能跳过有效保护期校验。
8. 推荐保护不改变候选人原有面试、审批及结果规则；本人获准推荐仍需通过现有岗位权限和流程校验。

## 十三 历史数据与上线规则建议

上线前只读盘点最近可能仍处于保护期内的历史推荐：确认推荐人身份、真实有效推荐时间、用人组织，以及多个简历记录是否对应同一候选人。

- 信息完整且可验证的历史记录，可以按原时间参与保护；不能从上线或迁移当天重新起算 15 天。
- 人才库上传时间、待解析占位创建时间、后台补录时间不能直接冒充有效推荐时间。
- 推荐人或时间不明确的记录，需要形成待核实清单，由业务确定补录、排除或其他处理方式，不自动编造归属。
- 若同一候选人已有多个推荐人且时间重叠，需要先确定历史保护归属，不能给多人同时建立互相冲突的当前周期。
- 若决定仅对上线后推荐启用保护，应明确历史记录不完整导致的保护覆盖范围，不能宣称全部历史推荐已受到保护。

历史启用策略需在上线前确认；不自动导入截图对应 TG 系统的外部记录。

## 十四 验收标准

时间相关用例按第六节建议口径编写，相关口径确认后固化为验收依据。

| 编号 | 验收场景                                | 预期结果                                                 |
| ---- | --------------------------------------- | -------------------------------------------------------- |
| AC01 | A 首次有效推荐候选人 C                  | 推荐成功，生成 A 的保护周期，默认 15 天                  |
| AC02 | B 在保护期内向同一组织推荐 C            | 拦截，显示历史人员、组织、时间及截止时间，不创建有效推荐 |
| AC03 | B 在保护期内向另一组织推荐 C            | 同样拦截                                                 |
| AC04 | B 与 A 属于同一招聘组                   | 仍拦截 B                                                 |
| AC05 | A 在第 10 天向另一个组织推荐 C          | 允许，增加历史明细，原保护截止时间不变                   |
| AC06 | 同一次推荐选择多个岗位及组织            | 保存各目标明细，组织摘要去重，共享一个保护周期           |
| AC07 | 提交时刻分别为截止前、恰好截止、截止后  | 截止前拦截他人；到达截止后按新周期规则处理               |
| AC08 | 修改保护期参数                          | 新周期使用新值，已生效周期保留原值；非法值保存失败       |
| AC09 | 更换文件名、修改推荐语或来源            | 已识别为同一候选人时，仍能命中保护                       |
| AC10 | 同名不同人、仅经历相似、联系方式冲突    | 不凭姓名或相似分数直接确定保护归属；展示相应依据         |
| AC11 | 检测服务异常或简历未解析完成            | 显示未完成状态，不完成有效推荐，不启动保护期             |
| AC12 | 单条、批量、人才库导入、智能推荐提交    | 均执行相同保护规则，强制继续参数不能绕过                 |
| AC13 | 批量同时包含可推荐与被保护候选人        | 逐候选人展示结果；冲突候选人的全部目标均不得成功推荐     |
| AC14 | 两名推荐人并发提交同一候选人            | 仅一人成为保护人，另一人被拦截                           |
| AC15 | 重复点击、请求重试、任务恢复            | 不重复推荐、不改变保护开始及截止时间                     |
| AC16 | 其他招聘组成员命中保护冲突              | 可见必要摘要；无权打开的完整简历与附件仍不可访问         |
| AC17 | 同一候选人出现在不同工作区              | 各自独立判定，不返回另一工作区的记录                     |
| AC18 | 仅上传人才库、AI 生成岗位建议、解析重试 | 不开始或延长保护期                                       |
| AC19 | 旧推荐人更名、调组、离职；简历归档      | 按确认后的生命周期规则保留归属与计时，不自动换保护人     |
| AC20 | 补录历史有效推荐或发现历史冲突          | 按上线策略处理，保留原时间依据，不从补录时间重新计时     |
| AC21 | 本次上传被保护期拦截 | 只在“全部”显示；AI 评价审核、简历筛选、面试、Offer 和已结案均不显示本条拦截记录 |
| AC22 | 历史原推荐记录正在真人复面 | 历史记录仍留在原阶段；保护详情显示其当前进度，不将本次记录视为已进入真人复面 |
| AC23 | 保护期中查看本次卡片 | 显示保护人与截止时间及有权限的继续推荐操作；不显示新评分或解析过程说明；原有资料与操作入口保持现状 |
| AC24 | 原保护期自然到期 | 本条仍在“全部”，显示待重新检测，不自动入库、分析或创建新保护周期 |
| AC25 | 点击重新检测并进入分析时出现新的有效保护 | 重新读取当前保护；显式确认仅放行本条记录，保留当前保护归属和期限 |
| AC26 | 重新检测失败后重试 | 检测失败保持未进入分析；确认成功后启动分析，启动失败可在 AI 评分重新评估 |
| AC27 | 批量选中包含保护期拦截记录 | 批量进入分析不直接放行；明确显示受限项，服务端逐条执行相同校验 |
| AC28 | 调整保护期天数后返回既有拦截记录 | 原周期截止时间不变；只有新周期使用新值 |
| AC29 | 查看普通及保护期卡片的右侧操作与更多菜单 | 原有简历、编辑、更多的位置和交互保持现状；菜单项目按原权限和条件显示，不因本功能重排或删改 |
| AC30 | 查看新增保护提示、详情及检测结果 | 使用保护人、组织、截止时间及是否可继续推荐的业务文案；不出现已解析、结构化提取、JD 分析未执行等新增过程说明；原有解析失败标签和重新解析菜单保持现状 |

首期验收重点为上述用例通过，以及每一次拦截均能说明候选人匹配依据、保护人和截止时间。上线后可观察拦截数量、身份误判、检测失败及不同入口漏拦情况；业务目标值由试运行数据确定。

## 十六 候选人管理页面与交互设计

### 页面位置与记录含义

基于现有候选人管理卡片布局，保持“全部、AI 评价审核、简历筛选、AI 面试、真人复面、Offer、已结案”的阶段导航，不增加独立的保护期招聘阶段。

本功能只在现有界面增补保护期内容。标题、说明、原有筛选工具栏、普通卡片资料、经历摘要、评价、分数和标签均沿用现状；不为说明保护期而改写其他候选人的内容。右侧“简历、编辑、更多”的入口、布局及交互不变，新增保护操作不替换它们。

实施时直接复用既有简历预览、编辑及更多菜单组件和事件处理，不按设计稿中的示例预览重新实现这些功能。

“只在全部显示”专指本次因保护期被拦截的上传。受保护的原推荐记录已经处于招聘流程，继续按原来的阶段与权限显示。原推荐人的保护周期、评价、面试或 Offer 不被本次上传改变。

为支持记录留痕，“全部候选人”同时展示已进入招聘流程的记录，以及已解析但尚未获准进入流程的本次上传。阶段页和各阶段人数仅统计相应招聘记录；有效推荐量、待审批量及成功通知均不包含保护期拦截记录。原记录与本次记录各用自身记录标识，不能为了统一候选人身份而覆盖成一条记录。

列表默认按现有列表规则排序，不增加永久的保护期置顶。上传完成后返回“全部”，定位并突出刚刚产生的本次记录，使用户能找到处理结果。

### 保护期中的卡片

卡片沿用现有头像、姓名、编号、资料区域及右侧按钮列。示例均为虚构数据。

| 位置 | 展示内容 |
| --- | --- |
| 姓名右侧主状态 | 新增琥珀色“保护期中”，点击可查看保护详情；受限记录不虚挂招聘阶段 |
| 基础资料 | 沿用现有岗位、上传人、用人组织、评估、面试官、时间等字段及其布局，不重命名为新的说明字段；不以历史记录代填当前记录 |
| 保护提示区 | “推荐保护人为王晓 · 剩余 9 天”；已推荐至技术中心、海外业务中心；完整截止日期时间 |
| 保护提示文案 | “该候选人处于推荐保护期”；只说明业务限制，不展示解析、结构化或分析调用过程 |
| 简历事实 | 沿用现有技能、年限及经历摘要，不调整原有展示内容 |
| 独立风险标签 | 原有“疑似重复 · N 条”可与保护标签同时存在；不混成一个状态 |
| 新增保护操作 | 在保护提示区内放置“查看保护详情”，不占用右侧原操作区 |
| 卡片操作 | 选定仅显示“查看保护详情”；暂不展示“继续推荐”按钮及其右侧的限制说明，不保留按钮占位 |
| 右侧原有操作 | 继续使用“简历、编辑、更多”及原有查看简历交互；按原有条件展示，不改成新的资料弹窗入口 |

本次没有运行 JD 分析，因此不生成或借用历史评分及评价。新增保护期文案不向用户说明“本次已解析”“尚未生成 JD 评价”“结构化结果”等处理细节。原有解析失败标签、重新解析操作及其他既有文案保持现状，不在本功能中顺带改写。

已选定的卡片展示为：姓名旁“保护期中”标签，加浅色保护提示区；提示区内显示保护人、剩余时间、历史推荐组织、截止时间及“查看保护详情”。本轮仅收敛卡片展示，不因隐藏继续按钮而改变保护期内禁止推荐的规则。

“更多”菜单继续保留复制详情链接、查看简历、重新解析、标记结案、删除等既有项目，按原有记录状态、权限及可重试条件显示；不因保护期统一增加、隐藏、禁用或重排菜单项。编辑、结案和删除沿用既有交互，不在本需求中重设规则。任何既有入口实际尝试创建有效推荐或推进招聘流程时，服务端仍执行保护期校验；修改或重新解析本次记录不能改变历史保护人、重置期限或绕过限制。删除本次上传也不影响原推荐人的保护依据。

### 保护详情

点击状态或“查看保护详情”打开详情窗口。窗口显示本次上传人与目标，明确“当前保护人”和“本次操作人”不是同一字段。

上方显示：保护人及招聘组、本轮首次有效推荐时间、当轮生效天数、保护截止时间与本次拦截结果。中部按历史推荐记录列出：用人组织、岗位、推荐人、推荐时间、当前招聘进度。不同组织的进度分别显示，不合并成候选人统一阶段。历史进度取查询时的最新状态；拦截发生时的判定另保留审计快照。

例如：技术中心 / 王晓 / 10 月 16 日 / 真人复面待反馈；海外业务中心 / 王晓 / 10 月 19 日 / 简历筛选。该进度仅说明历史记录，不表示本次上传已走到这些阶段。

下方给出身份匹配依据、冲突信息及最近检测时间。只有语义相似时不能伪装成联系方式已核实；示例中的手机号及姓名一致须有实际证据。无权访问的历史评价、手机号、文件和完整候选人详情均不因冲突窗口而开放。

### 状态与按钮

| 本次状态 | 卡片及详情提示 | 可点击的主要按钮 | 不可执行的操作 | 所在位置 |
| --- | --- | --- | --- | --- |
| 保护期中 | 保护人、组织、截止时间 | 查看保护详情、继续推荐（限有权限的上传人或管理员）；原有操作沿用现状 | 未确认就进入分析或推进招聘阶段 | 仅全部；确认成功后进入正常流程 |
| 保护已到期待重新检测 | 原保护期已结束，请重新检测后继续推荐 | 查看保护详情、继续推荐；原有操作沿用现状 | 未重新检测就自动进入流程 | 仅全部 |
| 检测失败或结果不可用 | 保护期检测暂未完成，请稍后重试 | 重试检测；原有操作沿用现状 | 将失败当通过、继续推荐 | 仅全部；此状态不能显示已确认保护有效 |
| 最终检测通过且提交成功 | 推荐已提交，使用现有阶段状态 | 按现有招聘流程执行 | 未经审批直接推进下一阶段 | 全部及 AI 评价审核 |

“保护期中”点击“继续推荐”后仅展示二次确认窗口，沿用本条记录已保存的岗位和组织，不重新选择岗位。服务端重新读取当前保护状态；确认只放行当前记录，随后进入分析，不改变原周期的归属或截止时间。取消确认不改变受理状态。

“保护已到期”的“继续推荐”在服务端完成最终校验及有效推荐提交，通过后才切入 AI 评价审核并排队分析；失败保持原记录，不生成重复记录。不要求用户重新上传简历，复用已保留的资料；资料变化导致匹配结果失效时重新核对。

系统不在保护到期时自动开始分析、不自动抢占新保护周期，也不自动发送成功推荐通知。继续推荐使用现有权限、受理状态、操作日志和分析队列，不增加规则引擎、开关或额外审批流程。

### 上传结果与批量结果

原有上传过程保持现状，不为保护期增设解释解析、结构化或 JD 分析调用的进度说明。命中保护期后，新增业务提示“该候选人处于推荐保护期”，提供查看保护详情及返回列表的入口；后台仍在解析后、JD 分析前执行校验。

批量结果逐候选人区分成功、保护期拦截及检测失败。同一候选人多个目标全部受限；其他可推荐候选人可独立成功。沿用现有批量操作入口，不新增与本需求无关的批量工具栏。任何入口都不能靠前端跳过受限项而绕过服务端校验；涉及受限项时显示业务原因。

### 参数维护界面

建议在现有“公司信息与话术”页面增加“招聘规则”区域，使用“简历推荐保护期 / 数字输入 / 天 / 保存保护期”。展示当前值、修改人和时间，保存后说明新旧值及“已有周期截止时间保持不变”。不改动原公司信息、话术及其既有保存方式。

管理员可修改；其他角色是否可见或可改仍按配置权限处理。普通上传人不能通过本次候选人详情修改全工作区保护时长。

### 首期完整路径

上传或导入 → 解析资料 → 共用向量召回和身份核对 → 独立产生疑似重复结果及保护期结果 → 命中保护则仅在全部保留本次记录 → 用户查看保护详情及历史进度 → 用户显式确认继续推荐后进入分析 → 最终校验及有效推荐提交 → 进入 AI 评价审核并生成评价。

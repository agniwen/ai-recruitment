# 0024：简历推荐保护期与招聘阶段分别记录

日期：2026-10-22

2026-10-23 展示范围调整：列表和候选人详情暂时隐藏“继续推荐”按钮及确认窗口，仅保留保护标签、摘要和“查看保护详情”；组件和后端能力暂时保留。下文继续推荐设计作为预留能力，重新开放前需补齐无岗位受保护记录的后续推荐路径。

同一工作区内，首次有效推荐为具体推荐人建立保护周期。保护期内其他人员向任何用人组织的上传默认拦截；本人追加推荐沿用原截止时间。默认 15 个连续日，配置修改仅影响新周期。

`studio_interview.resume_admission_status` 独立于 `pipeline_stage` / `outcome`，取值为 `pending`、`protected`、`accepted`。新增异步占位记录先为 pending；解析完成后，在事务内完成保护校验。受限记录只由全部候选人查询返回，招聘阶段查询、统计、分析任务和通知仅处理 accepted。为兼容既有阶段约束，受限记录的物理阶段仍为 ai_review；这个值不代表已进入 AI 审核。既有结案、删除和编辑交互保留，受理状态限制仍由服务端执行。

保护周期、有效推荐明细独立持久化，保存推荐人名称、当时的组织和岗位。删除候选人记录或人员离职不解除原周期。详情在原有可见性校验通过后，只返回保护归属、时间、组织、岗位、当前阶段等必要摘要，不返回跨团队的联系方式、简历文件、评价或历史记录链接。

疑似重复仍使用既有内容向量和检索逻辑。保护期不创建新向量、不增加 LLM 调用：使用已有文件 SHA-256，或规范化姓名与联系方式的组合建立强身份关联。联系方式明显冲突或只有语义相似不足以认定同一人。每次有效推荐保留身份快照，使后续版本的文件也参与匹配；查询不受同上传人排除、前十条展示限制或异步向量索引延迟影响。无法取得必要身份信息时保留 pending，不完成推荐。

工作区级 PostgreSQL 事务锁串行化归属判定与周期写入，避免两个人同时取得同一候选人的保护。数据库 CHECK 约束及面试/Offer 写入触发器兜底，防止旧入口绕过受理状态。单条、批量、人才库、智能推荐与独立分析接口执行同一规则。

已有记录默认保持 accepted，迁移不猜测首次有效推荐日期，也不因重新评分或解析自动开启新周期。上线前使用已核实的历史清单补录；没有核实的数据保持原招聘流程，但不会被伪造为新保护。操作方法见 [上线说明](../resume-recommendation-protection-rollout.md)。

界面沿用确认的方案：姓名旁保护标签、浅色保护摘要及“查看保护详情”，保留既有简历、编辑、更多菜单。增加“继续推荐”入口，限有简历创建权限的本次上传人或工作区管理员显式确认，并校验原关联岗位范围。确认窗口不再选择岗位，后端读取本条记录已保存的岗位；确认期间若岗位发生变更则拒绝过期请求，不覆盖岗位或组织。仅当前记录放行并启动既有分析队列；保护有效时沿用原周期关联以避免重处理再次拦截，不更换保护人、不修改截止时间，也不将放行记录写成原保护人的推荐。保护已到期则重新执行正常受理规则。确认使用既有候选人操作日志记录，重复提交不重复写确认日志。受保护详情以受理状态覆盖默认物理阶段，不展示 AI 评分或招聘推进动作。到期不自动分析或抢占新周期。

# 简历来源组织层级

招聘基础设置新增“简历来源”，关系为：简历来源 → 用人组织 → 部门。
它是招聘组织层级，独立于简历已有的 Boss、智联、内推等渠道字段。

## 设置流程

1. 在“招聘基础设置 → 简历来源”中新建来源。
2. 编辑用人组织，选择其所属简历来源；一个用人组织最多属于一个来源。
3. 在简历来源列表中“管理 ODC”或“设置 ODC”。序列、服务单位留空表示不限。

ODC 按岗位直接关联的简历来源访问岗位；简历可见性继续按岗位序列和服务单位筛选。调整组织归属、移除分配或取消成员角色的 ODC 标记后，后续请求按最新配置判定。

简历来源目前共用用人组织的页面权限及 CRUD 权限。仍有下属用人组织的来源不能删除，需先调整组织归属。删除来源会删除它的 ODC 配置。

## 发布

先应用 `apps/ai-recruitment-copilot/drizzle/20260908020000_add_resume_sources/migration.sql`，再发布应用。迁移只新增来源表、来源 ODC 关联表和用人组织的可空来源字段，不自动创建来源，也不迁移历史 ODC。

旧的部门／用人组织 ODC 记录保留，但不再参与授权。旧设置、单条增删改和批量设置接口返回 410；设置入口已隐藏。重新配置来源与 ODC 前，成员不会因历史 ODC 分配获得访问范围，其他招聘组或管理员权限照常生效。

## 从 Google 文档同步岗位

同步以表格的“来源表格”作为简历来源，也接受“简历来源”表头；两者同时存在时优先使用“简历来源”。岗位同时保存简历来源 ID 和用于展示、筛选的来源文本。

按当前工作区逐级匹配：简历来源名称 → 该来源下的编制组织名称 → 该组织下的部门名称。名称匹配会规范全半角、首尾及连续空格和字母大小写；命中已有节点时保留其原名称、描述和上级。不同来源下完全同名的用人组织及部门独立存在；同一层级内重复同步不会重复创建。已有未分配来源的同名组织也不会被搬到新来源。

来源为空时创建或复用“默认简历来源”；编制组织为空时在对应来源下创建或复用“默认用人组织”。部门为空的新岗位归入对应组织下的“默认部门”；已有岗位仅在父组织不变时保留本系统部门，否则归入新组织的默认部门，避免跨层级关联。

组织同步仅新增缺失节点，不修改或删除既有组织。岗位本身继续按唯一编码沿用原有更新和 Google 删除标记规则。同步结果会分别显示新增来源、用人组织和部门的数量。

## 招聘组负责范围

招聘组改为选择负责的简历来源。岗位授权按岗位的简历来源 ID 判断，修改岗位来源后立即使用新的范围，不再从岗位旧部门或旧用人组织推导。组织、部门仍按来源层级可见，同时包含已授权岗位所属部门。不同来源下同名组织不共享岗位授权；原无来源公共岗位规则保留。

旧用人组织分配记录保留，但不迁移、不再授予访问权限。管理员需重新选择简历来源。上线前应用 20260908040000_recruiting_group_resume_sources 数据库迁移。

## 岗位来源关联与历史回填

应用 `20260908130000_job_resume_source` 迁移后，岗位保存 `resumeSourceId`，以工作区与来源 ID 的复合外键防止跨工作区关联。迁移按当前工作区和规范化名称复用已有来源，缺失时创建；空来源保留为空，不搬动原有用人组织或部门，也不改写 ODC／招聘组配置。可重复执行。

岗位新建／编辑选择系统来源并提交 ID；新建来源成功后自动选中。来源改名同步更新关联岗位的显示文本，权限继续绑定原 ID；仍有关联岗位或用人组织的来源不能删除。Google 同步也写入该 ID。

ODC 简历可见性按关联岗位的来源以及配置中的序列、服务单位共同判断；撤销挂靠或取消 ODC 角色标记立即失效。招聘组的岗位范围按其负责的来源判断，简历原有的创建人、汇报关系规则保留。

## 预录入 ODC 配置

预录入新建／编辑选择标记为 ODC 的工作区角色后，可多选负责简历来源，并为每个来源设置序列和服务单位；留空表示不限。配置仅接受当前工作区的来源，角色判断使用角色的 ODC 标记。

注册时将配置写入简历来源 ODC 挂靠，招聘组为空也会生效。已有成员仍保留原工作区角色，实际角色不是 ODC 时不会新增挂靠。编辑同一邮箱的预录入信息会更新所选来源、解除本条预录入取消的来源，保留其他手动挂靠；更换邮箱不会撤销旧账号的配置。

先应用 `20260908143000_pre_registration_odc` 迁移，再发布应用。迁移为预录入记录增加默认空数组的 ODC 配置。来源若在注册前已被删除，注册时跳过该来源，编辑预录入时需移除失效选项。

## AI 评价审核

候选人管理新增流程起点：AI 评价审核 → 简历筛选 → AI 面试 → 真人面试 → Offer → 已结束。

新建简历、批量上传到候选人管理，以及从公共／私有简历池加入的记录，均先进入 AI 评价审核。更换岗位会重置评价并返回审核阶段。历史候选人不批量回退；在审核阶段结束的候选人，重新激活时仍返回审核，不能跳过审批。

审批资格由工作区角色的 `aiReview:approve` 权限控制。有该权限的角色可审批当前工作区全部处于 AI 评价审核阶段的候选人，不受简历来源、ODC 身份、序列或服务单位限制。管理员和拥有者默认拥有此权限。简历来源中的旧审批勾选项已移除，历史数据库字段保留兼容，但不再作为授权依据。

关联岗位且 AI 评价生成完成后，有权限的成员可点击“审批通过，进入简历筛选”，填写审批说明。审批会记录操作人、说明和阶段变化。未批准时保留在审核阶段，不能跳过审批推进面试。

首次启用审核阶段仍需应用 `20260909100000_add_candidate_ai_review/migration.sql`。本次角色授权调整无需新增数据库迁移，也不会自动向已有 ODC 角色授予全工作区审批权限。

### AI 分析审批工作台

“招聘工作台 → AI 分析审批”以分页表格展示当前工作区所有处于 AI 评价审核阶段的候选人，支持姓名搜索、候选人概览和 AI 评价。审批成功后候选人移出待审列表。

在“角色与权限”中新建或编辑审批角色，配置：

1. 页面浏览 → AI 分析审批。
2. 招聘流程 → AI 分析审批 → 查看。
3. 招聘流程 → AI 分析审批 → 审批。

前两项控制页面及待审数据访问，第三项控制审批操作。无需额外开放候选人管理、AI 面试管理或 ODC 身份。全来源访问仅限该工作区的待审队列，其他业务页面的数据范围保持原有规则。

### 管理员完整权限

工作区管理员和拥有者均从完整权限目录获得页面与资源权限，包含工作区删除。成员管理中可调整其他管理员和自己的角色；将现有成员设为拥有者会在事务内转移所有权，原拥有者变为管理员。最后一位拥有者不能直接被降级或移除，需要先转移所有权。

管理员可以管理本工作区其他成员的简历池记录，包括导入、发布、重新解析和删除。跨工作区隔离、候选人流程状态和审批说明必填等数据规则继续生效。平台级管理员是独立身份，不通过工作区角色授予。

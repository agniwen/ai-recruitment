# 简历推荐保护期：迁移与上线

本次迁移为增量迁移，新增受理状态、保护周期、推荐明细和保护时长配置。新周期默认 15 天；工作区“公司信息与话术”页维护保护天数，范围 1–365，原有公司资料的自动保存不会覆盖这个参数。周期保存独立的天数及截止时间。

## 应用数据库迁移

迁移文件为 `apps/ai-recruitment-copilot/drizzle/20261022120000_resume_recommendation_protection/migration.sql`。先确认数据库目标、备份及现有迁移状态，再按项目原有迁移流程执行 `pnpm db:migrate`。

2026-10-22 本地验证：已备份并迁移本机 `127.0.0.1:54324/ai_recruitment`，迁移前后候选人总数均为 203。全部候选人与 AI 评价审核列表的真实数据库查询均已成功返回。5 条尚未完成解析的旧占位记录按迁移规则标为 pending，其余 198 条保留 accepted。此记录仅代表本机开发库；线上数据库没有执行本次迁移。

生产切换时暂停上传/导入/分析写入任务，执行迁移和已核实历史补录，再同时启用新版本后端与队列 worker。新列默认 accepted 是为了兼容旧历史记录，不应让旧版 writer 在新版本上线后继续写入新候选人。数据库约束和触发器用于阻止受限记录产生评价或进入面试、Offer。

## 已核实的历史推荐

不能将旧文件上传时间或最近一次解析时间直接当作首次有效推荐时间。旧记录会保留原阶段、评价和招聘进度，不会统一从迁移时刻重新计算 15 天。

补录清单为 JSON 数组，必须来自业务已核实的记录、当时有效推荐时间和当时生效天数。例如：

```json
[
  {
    "recordId": "已核实的候选人记录ID",
    "recommendedAt": "2026-10-16T10:00:00+08:00",
    "durationDays": 15
  }
]
```

先预演。默认在事务内校验，最后回滚，不持久化补录结果：

```sh
pnpm --filter @arc/ai-recruitment-copilot-backend exec tsx src/scripts/backfill-resume-protection.ts --workspace 工作区ID --input /绝对路径/verified-recommendations.json
```

核对输出的记录与状态后，增加 `--apply` 持久化。脚本按真实推荐时间排序，同人同推荐人的有效追加推荐沿用旧周期；跨工作区记录、缺少身份或组织依据、推荐归属冲突、已有后续周期等会报错并回滚整批。已关联周期的记录再次执行会返回 existing。输出不包含联系方式、文件和数据库连接信息。

没有核实的数据不参与保护归属推断，需业务补充依据后再补录。不要通过直接修改候选人的受理状态解除保护。

## 界面验收

- A 向组织甲推荐后，B 在同工作区向组织乙推荐同一候选人：本次记录只出现在“全部”，显示保护标签、保护人、组织、剩余时间和截止时间。
- 点击“查看保护详情”：各条历史推荐显示原组织、岗位、推荐时间及查询时的招聘阶段。其他团队的联系方式、附件和完整评价不开放。
- 原有简历、编辑和更多交互沿用现状；列表及详情暂时隐藏“继续推荐”，仅保留保护标签、摘要和“查看保护详情”，不增加匹配依据或解析过程文案。
- A 追加向组织乙推荐不延长保护；B 被拦截的上传不生成新周期、不生成评价、不发成功或待审核通知。
- 批量结果区分推荐受限与正常完成；受限项不计为成功推荐，不进入各招聘阶段统计。
- 保护到期后，本条仍保留在全部候选人，不自动分析，也不自动建立新周期。“继续推荐”入口当前隐藏，组件和后端能力保留，重新开放前需补齐无岗位记录的后续推荐路径。

## 验证边界

开发验证包含身份策略、实际迁移、事务受理、周期边界、跨工作区隔离、历史日期补录、数据库绕过限制、评分任务、权限摘要以及卡片和已有操作的相关回归。PGlite 的并发提交测试运行在单连接执行器中；生产 PostgreSQL 的多连接竞争、真实上传队列及通知通道仍应在部署环境完成验收。没有运行生产构建或向真实 LLM/TG 发送测试请求。

预留的继续推荐能力验证：确认前显示保护状态、隐藏 AI 评分和招聘推进；确认后在原记录恢复正常流程，记录操作人并启动分析。服务端应拒绝未确认、越权、跨工作区、无权限或失效岗位、未就绪及已结案记录；重复提交不重复记账。当前入口不对用户展示；隐藏入口无需新增数据库迁移。

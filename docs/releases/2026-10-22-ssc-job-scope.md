# SSC 按岗位服务单位、部门分配 Offer

## 配置与匹配

“SSC 负责组织”新增“服务单位”“部门”两列，新增、编辑、来源中心内的 SSC 管理及数据导入均支持维护。
部门选择保存系统部门 ID；同名部门通过所属编制组织区分。
名称和所属编制组织都相同的记录额外显示简短部门 ID，短 ID 冲突时显示完整 ID，避免出现完全相同的选项。
服务单位可从已有岗位数据选择建议值，也可手动填写。

匹配依据是候选人当前选择的岗位：中心取岗位的来源中心，服务单位取岗位的服务单位，部门取岗位关联的部门。
Offer 信息确认弹窗中的可编辑展示内容不会改变路由依据。

- 中心必须匹配；服务单位、部门留空表示该维度不限。
- 填写服务单位后按去除首尾空格、忽略大小写的完整值匹配；部门按 ID 匹配。
- 两个维度均填写时，必须同时命中。
- 同时命中多个配置时，填写两个维度的配置优先于填写一个维度的配置，填写一个维度的配置优先于通用配置。
- 同等精度的多个 SSC 都保留，通知按 TG 私聊去重。
- 先确定最精确的责任配置，再核对 TG 绑定与操作身份。精确配置缺少可用 TG 时，不会将私人 Offer 内容转发给通用 SSC。

沿用当前 Offer 流程：先由招聘人员核对候选人私人 TG，确认提交后，再按上述规则创建和发送 SSC 通知。
SSC 接收确认、完成确认、审批截图以及候选人可见范围使用相同的匹配规则。
岗位或责任范围变更后，旧 TG 卡片再次操作也需要通过当前范围校验。

## 兼容与数据保护

- 现有配置的两个新字段均为空，继续按原中心范围匹配。
- 编辑 API 未传新字段时保留现值，显式空值表示清空该维度。
- 导入模板增加“服务单位”“部门”；旧模板仍可使用。导入的部门名称必须在当前工作区内唯一，否则预览提示错误，不猜测匹配对象。
- 同一身份可以维护同一中心的不同细分范围；完全相同的范围仍禁止重复创建。
- 已被责任配置引用的部门不能直接删除，避免删除后责任范围意外扩大。
- 修改责任配置不会自动批量补发历史 Offer。

## 部署

包含数据库迁移 `apps/ai-recruitment-copilot/drizzle/20261022190000_ssc_responsibility_job_scope`。
迁移增加两个可空字段、工作区与部门的复合外键，并扩展责任关系唯一索引。
先执行迁移，再部署 Web／后端与使用相同路由代码的通知 worker。
还需包含前一项 Offer 招聘确认功能的迁移和代码，不能仅替换前端静态文件。

本地部署不改共享机器人的正式 Webhook；常驻本地 worker 的 TG 外发配置保持关闭。
真实 TG 联调使用单独授权的临时窗口，不将模拟传输或数据库路由测试视为真实送达。

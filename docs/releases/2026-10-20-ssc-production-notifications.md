# SSC 正式环境 Offer 自动通知修复

## 修复的问题

新增 Offer 会在同一业务事务中创建 SSC 通知任务。旧实现第一次没有找到合格收件人时，会把空收件人任务标记为已完成；之后补齐 SSC 负责关系、节点权限或 Telegram 关注绑定，任务也不会再发送。

此外，已有机器人的 Webhook 可能只订阅了 `message`，缺少 `callback_query`，因此收得到文字却无法处理接收确认、完成确认按钮。

## 更新后的行为

- 新增或有效修改 Offer 后，Worker 根据应聘岗位的“部门/中心（来源）”匹配 SSC 负责组织，校验 SSC 审核角色、Offer 查看及接收确认权限、当前候选人范围和已验证的 Telegram 私聊绑定。
- 配置暂时不完整时，当前仍待接收的 Offer 通知保持待处理，每分钟重新匹配。等待配置不消耗 Telegram 发送失败的重试次数。
- 首次已找到 SSC、但发送前权限或绑定发生变化时，尚未尝试投递且无人收到的通知也会等待并重新匹配当前负责人；已经部分投递的任务继续保留收件人快照和去重记录。
- 自动恢复旧版本中“已完成、收件人为空、从未投递”的当前待接收通知。已送达的通知不会补发；旧修订、被替代、删除、取消、到期或已结案 Offer 不会恢复，历史接收/完成反馈也不回放。
- 卡片和免登录详情链接始终使用发卡 Worker 当前连接的数据库、候选人、Offer ID、SSC 修订号和公开域名，使用系统真实数据生成内容。
- Worker 启动及后续恢复检查会验证公开回调的鉴权，再为本部署配置消息和按钮事件订阅，保留其他已订阅事件与待处理更新。机器人已经指向其他环境时，不抢占其 Webhook，当前 Offer 任务继续等待。
- 无 Webhook 时也保留 Telegram 原有的默认事件订阅；鉴权探测后再次核对回调配置，检查期间入口被修改则暂停初始化。已就绪检查缓存五分钟，随后重新核对。
- 收件人限定的本地测试仍由临时联调入口管理，不自动调整共用机器人的回调，也不恢复其他历史通知。

SSC 无需邮箱或系统登录即可在机器人中操作。Telegram 只允许机器人向已建立私聊的数字账号发送消息；SSC 须先在本环境机器人私聊发送一次 `/start`，系统会校验实际 Telegram 用户名与数字身份。单独填写 `@用户名` 不会跳过身份、组织或权限校验。

## 发布

沿用仓库现有发布流程，同时更新 Web/Backend 和 Worker。两者使用同一正式数据库、同一 `BETTER_AUTH_SECRET`、Bot Token 和 Webhook Secret，并使用正式公开域名：

```dotenv
BETTER_AUTH_URL=https://recruitment.hirecopilot.bar
NEXT_PUBLIC_BASE_URL=https://recruitment.hirecopilot.bar
```

无需新增数据库字段或迁移。现有通知记录中的收件人、已投递人员、版本和租约校验继续用于并发控制及去重。

在“SSC 负责组织”中关联实际部门/中心和 TG；对应角色应启用“SSC 审核”，并授予 Offer 查看、SSC 接收确认、SSC 完成确认权限。现有角色的权限由管理员维护，发布代码不会扩大其他角色的审批权限。

更新后仍有效、尚未投递的空收件人任务会自动重新匹配，包括此前因权限或 TG 绑定缺失而漏发的 Offer。Worker 日志以 `offer-ssc-webhook` 输出固定原因码，例如 `different_environment`、`callback_authentication_failed`；通知任务等待收件人时记录 `ssc_recipient_unavailable`，日志不输出机器人凭据。

## 验证范围

回归用例覆盖真实创建 Offer、SSC 来源路由、无邮箱的 TG 身份、权限补齐后的自动投递、卡片和详情令牌绑定、空收件人恢复、已投递去重、失效版本排除，以及机器人回调初始化、鉴权、其他环境保护和启动重试。Telegram 网络传输在自动化测试中替代，数据库、权限和通知服务实际执行。

针对性回归共 78 项通过（后端 55 项、Worker 23 项），包含实际数据库集成；后端与 Worker 类型检查、Worker 的 Node 22 目标构建及本次 TypeScript 文件的 Ultracite 检查均通过。正式环境的真实消息投递和 TG 按钮同步需在发布后验收。

完整回归：后端 2,458 项通过、119 项按原有配置跳过，Worker 64 项全部通过，两者均为 0 失败。SSC 相关的 78 项针对性回归没有跳过。

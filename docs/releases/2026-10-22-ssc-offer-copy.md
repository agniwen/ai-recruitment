# SSC Telegram Offer 整块复制与确认流程（2026-10-22）

SSC 收到的 Offer 卡片使用一个可整块复制的文本块，包含当前 Offer 的候选人、系统记录编码、编制、薪资，以及该候选人所有已完成的真人面试情况。复制入口与 SSC 接收、完成确认及选填审批截图流程同时保留。

## 使用方式

- 在 TG 文本块中使用自带的复制入口，一次复制完整 Offer 和面试内容，不分段、不跳转复制页。卡片继续保留「查看候选人详情」及当前状态和权限允许的审批操作。
- 接收确认后，同一张卡片继续显示「完成确认」。点击后核对内部审批，可选择上传审批截图；上传后出现新的确认卡片，点击「确认完成」才更新 Offer。接收和完成权限继续分别校验。
- 初始通知、接收后的更新、内部审批确认及截图后的卡片使用相同的全文文本块；完成后的卡片保持最新状态。反引号、反斜杠、多行点评和 Markdown 外观的原始内容不会提前闭合文本块。
- 保存内容中的 `{{emoji:…}}` 字面模板保持原文，正常发送、更新卡片及 Markdown 失败后的纯文本重试都不会被 SDK 替换成表情或丢失模板标记。
- Offer 正文不再附加「待 SSC 确认」或「SSC 确认中」尾行。系统与卡片的确认进度独立保留，SSC 完成后的「offer审批已通过」文本继续保留。候选人原始点评中的相同字样不做全局替换。
- TG 内置复制会携带文本块格式。Windows 电脑版 TG 粘贴回聊天时，用 **Ctrl + Shift + V** 以纯文本插入；普通 Ctrl + V 会恢复代码块底色。机器人不能控制 TG 客户端内置复制入口写入的格式。
- 系统 Offer 信息弹窗及免登录详情页仍提供「复制 Offer 信息」，按相同模板复制完整文本和换行。复制操作不会创建 Offer 或执行 SSC 确认。

## 长度与权限边界

Telegram 普通原生 `copy_text` 按钮最多支持 256 字符。本次取消较长文本的分段按钮，完整内容优先使用单一文本块；短文本仍兼容原生复制入口。适配器在发送、编辑及 Markdown 重试时保留业务回调，并为并发消息隔离复制资料。

当消息超出安全长度预算时，整块省略并明确引导通过已授权的候选人详情查看、复制全文，避免 SDK 静默截断；内部审批与截图确认卡也保留详情入口。没有添加单独的「打开全文复制页」按钮。

数据沿用当前工作区、候选人、最高 Offer 版本、修订号、SSC 负责关系及身份校验。已完成的真人面试按面试时间排序，显示北京时间、内部及外部面试官姓名和点评；旧快照兼容行为见[面试情况说明](2026-10-22-ssc-offer-interviews.md)。

## 部署

本轮整块复制及确认文案调整没有新增数据库迁移、依赖或环境变量。更新 PR 中的 Web、Backend、Shared 代码，使用目标环境既有机器人、通知队列、公网地址及回调配置。

仓库不包含本机 Token、Chat ID、候选人测试资料、临时公网分流地址或测试进程。部署业务代码不会开启本地临时分流。标准数据库迁移按既有[Offer 创建确认说明](2026-10-21-offer-creation-confirmation.md#部署)执行。

## 验证记录

本轮回归先复现整块格式缺失和确认中文案未移除，再验证完整文本块、换行及特殊字符、全部已完成的面试情况、待接收/确认中/完成状态、接收后继续完成确认、截图上传后的最终确认按钮、权限校验、超长内容整体回退及普通消息透传。

本地真实 TG 联调已核对授权收件人收到 v11 的完整 Offer 与面试文本；保持系统已接收记录，重发卡片恢复「完成确认」，单一文本块与去除确认中尾行均通过真实 TG 回包核对。临时窗口限定单个测试 Offer 和收件人，其他更新转回正式系统；到期恢复原回调并关闭测试操作。测试卡片补充有效时间与到期提示属于本地联调脚本行为，不在正式业务代码中加入 30 分钟开关。

人工完整审批结果按实际系统状态记录，不将自动化截图测试或发卡成功视作正式环境全流程验收。PR 发布前的最终测试、类型与构建结果记录在 PR 描述中。
